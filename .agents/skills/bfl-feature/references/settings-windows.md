## Settings Window Principles

Use the redesigned default BetterFriendlist Settings as the interaction reference for BFL settings windows and editors. Choose patterns that fit the player's task and the available space.

- **Make the common path the shortest.** Put frequent edits directly on the field they affect. Use a toggle for on/off, a choice control for mutually exclusive values, and a button for an action. Give the main action in each area a clear visual priority. Put a small set of fixed actions directly on the relevant item or section when they fit without crowding its label. Use a menu for larger sets or choices that depend on the current data, and offer recovery actions when there is something to recover.
- **Organize around what players want to do.** Group controls by outcome and keep the current item or category easy to identify. When an entry point already identifies an item or option, select it and bring it into view. Add search or filtering when it helps players reach a target in a long list.
- **Use the same hover and pin behavior as Settings.** Hovering a settings row highlights the row, explains its effect, and marks the affected part of the preview when one exists. Clicking the label or empty row space pins or unpins the explanation and highlight. Keep the control itself available for its normal action. Apply this consistently to comparable rows, including color swatches and dropdowns.
- **Show the outcome with a representative preview.** Reuse the display renderer where practical. Label the preview's context and whether it shows saved settings or a draft. Keep trial changes within the preview or draft. Add a saved-versus-draft comparison when it helps players make a choice, and show hidden or unavailable states explicitly.
- **Make saving and destructive actions predictable.** In editors with drafts, preserve them while switching items, mark what is pending, and make the scope of Apply, Save All, Discard, and Reset clear. Keep a reset in the draft when the editor uses explicit Apply. Describe the concrete impact before confirming a destructive change.
- **Keep choices when a parent option disables them.** Show dependent controls and their current values in a disabled state when the relationship matters. Restore their prior effect when the parent option is enabled again.
- **Use familiar BFL controls and adapt to the space.** Reuse existing controls, theme styling, and visual states. Let help and previews stack when space is tight. Check that the current selection and key actions remain reachable with narrow layouts, small UI scale, and long localized labels.
- **Make list structure and drag feedback visible.** Indent child entries consistently, including entries that cannot move. Give action and menu buttons a visible hit area and hover state. Label icon-only actions with tooltips. For reorderable rows, show a drag ghost and a separate insertion marker.

For the Friend Tag Editor, check the common paths from an already selected tag. The displayed icon should open the picker in one click. Offer a custom icon path inside the picker and keep Remove Icon available beside the icon control. Visibility switches should update the draft preview directly, with one Apply action to save the edits. Give New Tag clear priority at the list, keep section creation with section management, and show Restore Tags when removed tags are available. Check that players can find the icon, text, and visibility controls at a glance and that switching tags keeps their draft.

### Visual and interaction acceptance

- For work described as matching Settings, identify the existing controls and style owners for backgrounds, separators, menus, and interaction states. Reuse them where they apply. Record any deliberate deviation and why it is needed.
- Before handoff, capture the reference Settings and the changed UI side by side with the same client or simulator build, theme, and UI scale. Compare window surfaces, spacing, separators, control appearance, and hover and pin states. Check the normal and narrow layouts where the editor changes its layout.
- Exercise click paths from the state a player starts in. In a list with item actions, use a button or menu on an unselected row. Verify that it targets that row and preserves unrelated drafts. Check that the selection only changes when the action needs it. Verify other shortcuts from their actual UI controls.
- Report simulator and live-client checks separately. If native visuals or input could not be checked in WoW, state the remaining verification explicitly.
